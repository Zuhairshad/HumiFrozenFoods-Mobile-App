# Security audit of `api/`

Date: 2026-10-26. Reviewer: an adversarial code review by an AI agent, run against our own code. **This is not a penetration test and not a compliance certification** (no PCI DSS, GDPR or other statement). Nothing was sent to any real host; every attack ran in-process (`app.request`) against `mongodb-memory-server` with a fake Stripe gateway. It supplements, and does not replace, the human review the README requires before real payments.

## 1. Scope and method

- Read in full: `docs/api-contract.md`, `docs/SECURITY.md`, `docs/site-contract.md` sections 8-10, `api/README.md` and all of `api/src` (app, composition, bootstrap, config, middleware, lib, auth, routes, services, payments, orders, repositories, enquiries, catalog, scripts, jobs).
- Verified the claims in `docs/SECURITY.md`; the "planned" items (orders route, order repository, webhook route, expiry job) now exist and were tested (section 3).
- Wrote attack tests in `api/tests/security/` (`npm run test:security`, 292 tests, real MongoDB, all green). Where a defect was found, the failing test was written before the fix.
- Areas: guest-token forgery and IDOR, NoSQL/prototype/log/header injection, stored XSS, price/quantity/promo/slot logic, idempotency and races, webhook forgery and logic, DoS and rate limits, data exposure (recursive response scans), logs (canary secrets through every route), CORS and headers, a Mongo command-monitor allow-list, fail-closed configuration, dependency audit.
- Not covered: the real Stripe SDK/network behaviour, the owner's real Atlas data and indexes, deployment (Vercel headers, IP forwarding), the Expo app, the website API, load testing, anything needing a live card.

### Checked and found sound (regression tests exist)

- Guest tokens: payload re-pointing, expiry extension, `alg:none`-style and empty MAC, kid confusion (`none`, `__proto__`, `constructor`), foreign-key signatures, expired and future-dated tokens, replay across orders, token in query/cookie/other headers, absurd Authorization values: all 401/403, never 5xx.
- Lookup: identical response for missing, wrong-contact and website orders; per-IP and per-order-number limits; both factors must match when both supplied; coarse timing check (medians within 20 ms; this cannot prove equalisation, code review shows hashing is always performed).
- Injection: operator objects, dotted keys, `__proto__`/`constructor`, repeated and bracketed query params, regex metacharacters and catastrophic patterns in `q`, malformed percent-encoding, 90 KB nested JSON, CRLF/NUL in names, emails, notes, headers: 400, no prototype pollution, nothing stored. Log lines stay valid JSON. XSS payloads round-trip as inert text over JSON with nosniff and a `default-src 'none'` CSP.
- Pricing: every client price field rejected (strict schemas), invalid quantities (0, negative, fractional, huge, strings, null), merged duplicate lines identical to one line including the free-delivery boundary, integer-pence sums equal an independent computation, discount never exceeds subtotal, zero/sub-30p totals refused before any order or Stripe write, ASCII-only promo codes (fullwidth, dotless i, long s, Kelvin sign all rejected), no stacking. Slot dates: 2026-02-30, wrong formats, past, +15 days, same-day lead time.
- Webhook: missing/garbled/stale/wrong-secret signatures, one-byte body change, oversized and chunked oversized bodies, non-POST, wrong content type; forged metadata, website orders, other orders' intents, amount/currency mismatch, monotonic transitions, partial vs full refund, parallel duplicate delivery (exactly one `applied`), replay changes nothing.
- Data exposure: recursive scan of every response (no `b2b_pricing`, `sold_quantity`, `sku`, `__v`, `stock`, intent ids, other customers' PII; `clientSecret` only in the checkout response); opaque 500s in production; `/readyz` hides driver text. Canary secrets, PII, tokens and client secrets never appear in trace-level logs across all routes, including error paths.
- CORS exact-origin matching (suffix, case, port, scheme, `null`, `*`), 403 for writes from other origins, hardening headers on all response types, `no-store` on everything except catalogue reads.
- Mongo command monitor over a full flow (checkout, replay, races, webhook paid/failed/refunded, lookup, enquiry, catalogue, expiry): only `insert/update/findAndModify/find/aggregate` plus handshake; orders inserts always carry `app_meta.source=mobile-app`; every update filter does too; no delete, no index or collection changes, nothing written to `products`; index definitions touch only `webhook_events`, `app_idempotency`, `app_enquiries`.
- Production safety: no Stripe config gives 503, no order, webhook 400 and `payments.enabled=false`; production config refuses missing Stripe/token keys/public base without echoing values; the fake gateway and dev mock server are not reachable from the production import graph (static check).

## 3. Verification of `docs/SECURITY.md` claims

All "planned" routes and the expiry job exist and behave as described. The webhook does mark paid only after source, order, intent, amount and currency checks. Two caveats: `SECURITY.md` does not mention F-02 or F-09, and the reverse-proxy IP case (F-12) is still configuration-dependent.

## 4. Residual risks (plainly)

1. Rate limiting is per instance (F-10, F-11). Until a shared store or WAF exists, checkout, lookup and enquiry abuse limits are soft.
2. The database credential can modify every order in the shared collection; the code only updates app-created ones (proved by test) but a leaked `MONGODB_URI` is a leak of all orders.
3. Paid-after-cancel needs a human (F-09).
4. Guest tokens cannot be revoked; lookup needs only an order number plus one contact field.
5. Stock is not reserved; promo codes are unlimited-use.
6. The order document shape and Stripe metadata propagation to charges (`charge.refunded` relies on it) are unverified against the real systems.
7. Free text is stored verbatim; rendering safely is the job of the admin portal and any mailer.
8. Unit test `tests/unit/payments/checkout-slots.test.ts` ("constants still match the app source") was failing during this audit because another change edited `src/features/checkout/slots.ts`; unrelated to the audit but unresolved.

## 5. Must be done by a human before launch

- Set `NODE_ENV=production` on every host, and `TRUSTED_IP_HEADER` to a header your platform overwrites (e.g. `x-real-ip` on Vercel). Send a request with a forged `X-Forwarded-For` and confirm the limiter ignores it.
- Replace the in-memory rate-limit store with a shared one or WAF rules; add bot protection to checkout and enquiry.
- Create an index on `orders.tracking_number` yourself (the API must not), then re-check lookup latency.
- Schedule `npm run jobs:expire-pending` and alert on log messages `payment_not_applied`, `payment_amount_mismatch`, `webhook_intent_mismatch`.
- Run `npm run verify:schema` against the real orders collection; confirm with a Stripe test-mode refund that `charge.refunded` carries `metadata.source`.
- Use test-mode keys end to end first; confirm the website's own webhook ignores our events; keep MFA on Atlas, Stripe, Vercel, GitHub.
- Decide on promo policy (single-use, per-customer) and stock reservation.
- Rotate any secret ever pasted into chat or logs; enable secret scanning.
- Commission an independent penetration test with a test-mode environment, and a privacy/compliance review (retention of enquiries and idempotency records).
